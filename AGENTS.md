# House Expenses Tracker — Agent Guide

## TL;DR
```bash
pip install -r requirements.txt   # install flask
python3 main.py                   # run web server — sign up via browser
python3 main.py --port 8080       # custom port
python3 main.py --host 127.0.0.1  # custom host
```

Open browser at `http://localhost:5000` (port set in `config/settings.py`).

## Architecture

| File | Role |
|---|---|
| `main.py` | Flask entrypoint — app creation, secret key, CLI args (`--host`, `--port`, `--debug`) |
| `routes.py` | All routes, decorators, permission helpers, context processor (`register_routes(app)`) |
| `config/settings.py` | Constants: `PORT`, `MONTHS_INDEX`, attribute lists, `USER_DB_DIR`, `USERS_DB` |
| `db/sql_manager.py` | `SQLManager` class + `generate_user_db_sql()` — SQLite data access layer |
| `db/init.sql` | Legacy per-user DB schema (default attributes) |
| `utils.py` | Helpers: `parse_date_bound`, `get_color_for_attribute` |
| `init_app.py` | Initialization — creates dirs, `users.db`, `flask_secret.key` |
| `templates/` | Jinja2 HTML templates (one per feature) |
| `static/css/style.css` | CSS |

## Key facts

- **Language**: Italian — month names (`GENNAIO`, `FEBBRAIO`, …), all UI strings. Keep it consistent.
- **DB**: SQLite only. Flask is the only external dependency.
- **Auth**: Multi-user via `users.db` (central) + per-user SQLite DB in `data/user_data/`. Signup creates a fresh DB with custom attributes via `generate_user_db_sql()`. Login sets `session['db_path']`.
- **Port**: Set via `config/settings.py:PORT` (default `5000`). CLI override: `--port`.
- **Secret key**: Persisted in `flask_secret.key` so sessions survive server restarts.
- **Computed columns**: `uscite_variabili`, `uscite_fisse`, `uscite_totali`, `delta` are maintained by SQLite triggers (generated by `generate_user_db_sql()`). Do not touch them from Python.
- **Year**: Stored in Flask session (`session['year']`). Defaults to current year on first visit. Change via `/change-year`.
- **Attribute management (profile)**: Users can add/remove/reintegrate custom variabili/fisse attributes and set fixed-expense defaults from their profile page. **Columns are never dropped** — removal zeros the column from the current real month onward, keeping history intact. Lifetime is tracked in `users.custom_attribute_history` (JSON dict `attr → {"type": …, "periods": [[start,end],…]}`; null start = "from the beginning", null end = "still active"; period is `start ≤ month < end`). Active lists `users.custom_variabili`/`users.custom_fisse` (JSON) are derived from the history; defaults in `users.custom_default_fisse` (JSON dict col→amount). `routes.normalize_attribute_history()` backfills history for legacy accounts (or empty history) from the physical column layout, and `routes.parse_custom_lists()` falls back to the canonical column layout for accounts whose lists were never stored.
- **Temporal masking**: All data pages (`add-expense`, `comparison`, `tracking`) are masked per month — an attribute only shows for months where it was active. Column order is *canonical*: `mese, entrate, [variabili…], uscite_variabili, [fisse…], uscite_fisse, uscite_totali, delta`, so physical column position (appended at the end by `ALTER TABLE`) never leaks into the UI. Rows are realigned via `dict(zip(physical_cols, row))` (helpers `get_effective_columns`, `get_canonical_columns`, `effective_month_view`). `current_month_key()` (= real `datetime.now()` month) is the activation/deactivation boundary.
- **Fixed-expense defaults**: `add_month_entry(month, default_fisse=dict)` pre-fills fixed columns when a new month is created and creates a `registro_spese` entry (`nota='Default'`) for each non-zero default so that defaults also appear in the storico. `routes.ensure_month()` creates missing months with the current defaults and then calls `sync_default_months(sm, username)` for every existing month; `set_default_fisse` also calls the sync right after saving. The sync (`routes.sync_default_months()`) re-applies the current defaults to **every existing future month** (`month_tuple(month) > current_month_key()`, i.e. strictly after the current real month) and only for attributes **active in that month** (helper `defaults_for_month()`), so **editing a default propagates to already-created months too**. Columns that contain user-entered data (any `registro_spese` entry whose `nota` is not `'Default'`) are never touched; for unprotected columns the sync creates, updates or removes the `'Default'` registro entry and adjusts the cell accordingly. Clearing a default removes the registro entry and zeros the cell. Current/past months are never touched. Removing an attribute **clears its default** from `custom_default_fisse` (past real values in the column are untouched); reintegrating brings the attribute back with **no default (0)**. `set_default_fisse` rebuilds the stored dict from the currently active fisse only.

## Gotchas

- `db/init.sql` is **out of sync** with `generate_user_db_sql()` — it has hardcoded default attributes. New users get dynamic SQL. `init.sql` is legacy only.
- `push_db.sh` and `test.sh` are local-only scripts, gitignored, not part of the project workflow.
- No tests, no CI, no linter, no formatter.
- **SQLite `DROP COLUMN`** fails if triggers reference the dropped column, and dropping would destroy past data. A removed attribute keeps its column: `SQLManager.remove_attribute(name, from_month)` zeros the column in every existing month `>= from_month` (boundary compared in Python via `_month_tuple`, never by string) and leaves triggers untouched. `add_attribute()` still does `ALTER TABLE ADD COLUMN` (appends physically at the end) and recreates the triggers with the **full historical variabili/fisse lists** (`_recreate_triggers`), because triggers need every ever-used column since removed ones must keep contributing 0. Attribute type per column comes from `users.custom_attribute_history`, not from physical position.
- **Minimum columns**: a user must always keep at least one active variabile and one active fisso attribute; the profile route refuses to remove the last of either (active for the current month, history-based).

## Conventions

- All SQL queries use **parameterized `?` placeholders** — never interpolate values directly. Dynamic column names are validated against actual DB columns via PRAGMA.
- Month format in DB: `YYYY_MESE` (e.g. `2026_GENNAIO`).
- Routes are defined inside `register_routes(app)` in `routes.py`. Each page handles both display (GET) and action (POST) — results render on the same page.
- New features: add route in `routes.py`, create template in `templates/`.
